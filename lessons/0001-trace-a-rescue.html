Lesson 01 · placement prep · 10 minutes

Trace one rescue from request to receipt

Your first win is not memorising the repository. It is being able to follow one meaningful action across the UI, API, domain logic, database, and realtime layer.

Mission link

This gives you the backbone for a two-minute project explanation in a placement interview.

The mental model

Every feature trace starts here.

User actionDonationForm sends JSON.
Route handlerAuthenticates, authorizes, validates.
Domain serviceOwns rules and transaction.
DatabaseStores state plus history.
ObserversNotifications, SSE, and Ably.

Rule of thumb: route handlers are the boundary; services are the brain; Prisma models are the vocabulary; workers finish time-based work after the request ends.

Follow the actual code

Open each file in order.

  1. components/donor/donation-form.tsxThe donor collects food details, pickup time, address, and coordinates, then sends POST /api/donations.
  2. app/api/donations/route.tsThe API boundary gets the session user, requires the DONOR role, rate-limits, parses the Zod schema, and calls the service.
  3. createDonationForDonor()The service geocodes if needed, ranks the top three NGOs, and opens a Prisma transaction that writes the donation, status events, candidate rows, notifications, and live-event outbox records.
  4. respondToMatchCandidate()When an NGO accepts, updateMany only claims a donation whose assignedNgoId is still null and whose status is matchable. That database condition makes “first acceptance wins” safe under concurrency.
  5. requestVolunteerForDonation()The assigned NGO requests a volunteer. The service finds a fresh, nearby candidate, creates an OFFERED assignment, and notifies the volunteer.
  6. workers/rescue-offers.tsThe worker expires offers, dispatches the next eligible volunteer, and publishes pending live events with retry behavior.
  7. verifyPickupOtpForVolunteer()After a trusted geofence arrival, the donor receives a short-lived OTP. Verification advances the assignment toward the NGO and advances the donation to picked up.
  8. confirmRescueDelivery()At the NGO geofence, the assigned NGO confirms receipt. The assignment and donation become DELIVERED, and the audit trail plus observers are updated.

Notice the two clocks

Overall request vs delivery attempt.

Donation

REPORTED → MATCHING → NOTIFIED → ACCEPTED → PICKUP_IN_PROGRESS → PICKED_UP → DELIVERED

This answers: “What is happening to the food request?”

Assignment

OFFERED → ... → ARRIVED_AT_NGO → DELIVERED

This answers: “What is happening to this volunteer attempt?” A failed or expired attempt can be replaced.

Retrieval practice

Answer before rereading the trace.

Where should the first-acceptance business rule live?

How does the system prevent two NGOs claiming one donation?

What makes live-event delivery recoverable?

Say it in an interview

Use your own words next.

“I would trace a donor submission from DonationForm to the donations route handler, then into createDonationForDonor. The service performs matching and writes the donation plus its audit and notification records in one transaction. NGO acceptance uses a conditional update so concurrent requests cannot both claim the same donation. Volunteer delivery is a separate assignment state machine; a worker handles offer expiry and retries, while geofences and OTPs protect the handoff. The database remains authoritative, and realtime is a projection for the UI.”

If you can say this without reading it, you have the first layer of project fluency.
